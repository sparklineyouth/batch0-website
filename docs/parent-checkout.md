# Parent payment and cohort admission

The student or a staff member with `applications.review` creates an invitation from an accepted application. `POST /api/stripe/payer-link` returns the exact tuition, expiry and a `/pay#token=...` link. Creating a new invitation revokes the previous token. The link is valid for at most 24 hours and never beyond the cohort's enrollment deadline. It grants payment access only; it cannot read application answers or sign into the student's account.

Tokens contain 256 random bits. Only a domain-separated SHA-256 hash is stored. The fragment is removed before analytics runs, API responses use `no-store` and `no-referrer`, and API failure logs omit raw requests and Stripe errors. Neither the link nor the token should be copied into application logs or analytics. A payer's Stripe session does not use the student's saved Customer object or saved cards.

The invitation snapshots the student's regional tuition, active promotion, Founder Pass and awarded scholarship. A parent's geography never changes that quote. Prices use the shared `quoteTuition` calculation. A positive USD remainder below $0.50 is waived to $0 rather than rounded up; `residualWaiverCents` and Stripe metadata record that waiver, and the ledger records $0 actually collected. Promotion, pass and scholarship reads are strict: a database failure stops quoting/payment instead of silently charging a higher amount. A snapshot is honored during its short validity window; a newly generated link reflects newer awards/pricing. If a checkout is already reserved, both student and parent see and reuse that reservation's existing quote. Existing application rows without `pricing_country` use the student's current region when the student starts checkout or creates an invitation. Staff-generated invitations for such legacy rows use standard tuition; have the student generate their link when a regional rate applies.

## Capacity and completion

Deploy migrations `0080_revenue_ledger.sql` then `0081_parent_checkout.sql` before this code. `0081` adds cohort `late_entry_until` and `catch_up_plan`, application `pricing_country`, private payer links and checkout reservations. The separate Fall schedule migration supplies the authorized dates and catch-up terms.

An upcoming cohort honors `applications_close_at`. Once the cohort starts, enrollment requires an explicit unexpired `late_entry_until` and a catch-up plan. Cohort start/end days are interpreted in America/New_York. Completed, canceled and ended cohorts remain closed. Server application submissions enforce the same rule even when a client bypasses the form.

Checkout reserves a seat under a cohort row lock for 35 minutes, and Stripe Checkout expires at that same instant. Capacity includes both enrollments and unexpired reservations. Concurrent student/parent clicks reuse one reservation and a Stripe idempotency key, preventing duplicate checkouts. A database trigger makes manual enrollment honor reservations too. Only card methods are enabled, avoiding delayed bank-debit settlement after inventory is reallocated. The Stripe amount is built directly from the stored quote; an old fixed Stripe Price cannot override it.

The reservation, pending ledger row and Stripe session are linked before the checkout URL is returned. If an external call has an uncertain outcome, the reservation remains held until expiry rather than risking an oversold seat. A successful payment atomically writes the captured amount and consumes its reservation. Webhook replays cannot create duplicate enrollment or resurrect a refunded application.

Stripe returns to `/pay#session_id=...`. `POST /api/stripe/payer-status` checks the session's reservation and application metadata, retrieves the actual Stripe state, and runs the same fulfillment used by webhooks. It exposes only `confirmed`, `pending` or `review`. Query parameters alone never prove payment. A valid charge that cannot be enrolled—capacity reassigned after an expired reservation, withdrawn application, quote mismatch—remains in the money ledger and reports `review`; staff must resolve it. A fully refunded charge cannot grant access. No refund policy is changed.

## Verification

Run `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --test lib/cohort-eligibility.test.ts lib/parent-checkout-db.test.ts lib/tuition-quote.test.ts lib/checkout-service.test.ts`. The tests run the actual migration in isolated PostgreSQL-compatible PGlite and cover last-seat competition, manual overbooking, retries, quote preservation, revoked admission, actual captured amount, refund-before-fulfillment, admission cutoff, expired holds, permissions, Eastern midnight and token entropy/expiry. Mocked integration tests also exercise the real HTTP handlers and service for owner/staff authorization, parent/student reuse, private response fields, invitation rotation, post-Stripe database failure and retry, zero-dollar orders, provider review states and pricing outages. They do not contact production Stripe or Supabase.
